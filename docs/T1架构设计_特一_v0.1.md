## 0. TL;DR

T1 是把 HEv7.0 的「多专家 + 路由 + 协作协议」这一层**整体卸掉**后，留下的一个**单核、受约束、生成式**主线：

- **CLM 字符引擎**先把 query 拆成字符/语义原子、识别领域、抽取关键变量，输出【分析上下文】——它同时决定了"这次要用哪些规则"。
- **RPF 核心 = 规则引擎（选规则 + 裁决）包裹 概率引擎（生成）**：规则引擎依据【分析上下文】**只选出本次任务要用的规则子集**（不是把所有规则全在启动时加载），再用综合名单 / Trie 对概率引擎的每一步 logits 实时裁决（硬 −∞ / 软降权 / 白加成 clamp≤原始）。
- **TRA 推理控制器（第二步·搜集信息）**：对草稿做三反思（一致性 / 合规 / 完整性），把修订指令回灌生成（可多轮），对外调用 百度 / QT浏览器（⚠ 占位：QT浏览器尚未开座）。
- **变量引擎（7.5 提前）**：面向长文本，变量树（主变量 + 子变量）、变量↔变量关系、某关系调整是否影响第三个变量；产出排除结论参与约束裁决。
- **因果引擎（7.5 提前）**：**双角色**——训练期 L_causal 注入 + **推理期分支仲裁**（为候选续写打因果充分性分，与变量引擎共同择优）。
- **概率引擎**：最终把所有上下文（分析上下文 + 规则约束结果 + TRA 修订 + 变量/因果结论）汇总，**生成最终回答内容**。

一句话：**T1 = CLM 分析 → RPF 核心（规则选裁 + 概率生成）→ TRA 反思回灌 → 变量/因果引擎 → 概率引擎定稿**。

## 2. T1 设计目标与约束

- **G1 单核**：整个模型主体 = 一个 RPF 核心，无多专家、无路由层。
- **G2 生成式**：必须有真实的「生成」能力（自回归产出 token 序列），而非仅分类/路由。
- **G3 受约束**：生成全程受规则引擎（综合名单 / Trie）实时约束，安全/合规/领域红线与生成解耦、各自可独立迭代。
- **G4 规则子集化**：规则引擎依据分析上下文**只加载本次相关规则**，不把所有规则常驻启动（见 §3 说明）。
- **G5 确定性引擎前置/专训**：变量引擎在长文本推理环节参与；因果引擎在训练期注入；二者均不占生成参数预算。
- **G6 轻量可训**：主体受 MX150 2GB 硬约束，规模先稳住 41M 级，目标逼近 0.124B；不引入外部大模型。
- **G7 隔离安全**：代码在 `T1/src/t1/`，不触碰现有 HEv6/7 训练产物，可逆、可对照。

## 3. T1 架构拓扑（修订版）

T1 的运行时数据流（单核主线）：

```
用户 query
   │
   ▼
[CLM 字符引擎] ── 问题分析：字符/语义原子拆解、领域识别、关键变量抽取
   │  输出【分析上下文】（领域标签 + 关键变量 + 拆解结论）
   ▼
[RPF 核心 · 规则引擎] ── 依据【分析上下文】①【选择本次要用的规则子集】
   │  （不是全量启动：规则引擎必须先知道这次用哪些规则才能裁决）
   │  ② 综合名单/Trie 裁决：硬 −∞ / 软降权 / 白有效加成(clamp≤原始)
   │  ③ 约束后的 logits →【概率引擎】采样/贪心 → 下一个 token
   ▼ （循环至 EOS 或长度上限）
生成初稿
   │
   ▼
[TRA 推理控制器 · 第二步 · 搜集信息] ── 三反思：一致性 / 合规 / 完整性
   │  修订指令回灌生成（可多轮）
   │  对外调用：百度 / QT浏览器（⚠ 占位：QT浏览器尚未开座）
   ▼
[变量引擎 · 7.5 提前] ── 长文本变量图：确定变量、变量↔变量关系、
   │  某关系调整是否影响第三个变量（PropagationEngine 传播）
   ▼
[概率引擎] ── 汇总全部上下文（分析上下文 + 规则约束结果 + TRA 修订 + 变量/因果结论）
   │  → 生成最终回答内容
   ▼
最终回答

（训练期专用，不在推理主链）
[因果引擎 · 7.5 提前] ── L_causal 因果一致性，注入概率引擎训练
```

### 3.1 为什么规则引擎放在概率引擎之前（关键澄清）

> **问题**：CLM 之后接的为什么是「规则引擎」而不是「概率引擎」？
>
> **答案**：规则引擎**必须先知道本次要用哪些规则**才能裁决；而"要用哪些规则"只能由 CLM 的【分析上下文】（领域、关键变量）来定。总不可能把全部规则（131 领域、上万条）全在启动时加载、每一步都扫一遍。**所以规则引擎先根据分析上下文选中"本次相关的规则子集"，再对概率引擎的 logits 做实时约束。** 概率引擎是真正的"生成器"，它躲在规则引擎的约束循环里被调用——规则引擎是这条支路的"门面"，因为它承担的是"选规则 + 裁决"这一区分性职责。

因此 RPF 核心 = **规则引擎（选规则 + 裁决）包裹 概率引擎（生成）**，二者在同一生成循环里协作，而非前后两个孤立阶段。

### 3.2 组件清单（T1）

- **CLM 字符引擎** —— 问题分析流水线（沿用 7.0，引用 `src/services/clm/`）
- **RPF 核心 · 规则引擎** —— 按分析上下文选规则 + 综合名单/Trie 裁决（复用 `composite_list.py` + `logits_processor.py`）
- **RPF 核心 · 概率引擎** —— 自回归生成器（T1 新增主干，`T1/src/t1/rfp_core.py`）
- **TRA 推理控制器** —— 三反思 + 多轮回灌 + 外部检索（沿用 7.0，引用举一反三/TRA 模块；外部检索占位）
- **变量引擎** —— 长文变量追踪/关系传播（7.5 提前，复用 `variable_engine.py`）
- **因果引擎** —— 因果一致性（7.5 提前，训练期 L_causal；复用 `CausalConsistencyLoss`）

### 3.3 移除清单（T1 不含）

- RPF-MoE 专家池、WoE 路由/管理层、AI 协作协议（共享白板并行版 + 分歧仲裁）

## 4. RPF 核心 = 受约束生成式模型（T1 最核心的新机制）

### 4.1 为什么「规则 + 概率」就是生成式模型

HE 历来把 RPF 定义为「规则引擎 + 概率引擎 + DeviationValidator」三者挤在一个专家里。T1 把这一组**抽出来、放大为唯一主体**，并重新分工：

- **概率引擎 = 生成器**：一个自回归语言模型（字符级 / 子词级均可），给定上下文产出 next-token 的 logits，逐 token 拼出回答。
- **规则引擎 = 约束器 + 选规则器**：把综合名单（硬/软/白）与 Trie 红线，**在每一步生成时对 next-token logits 施加裁决**；且**依据 CLM 的分析上下文只加载本次相关规则子集**（见 §3.1）。

二者解耦：生成能力在概率引擎（越训越强），安全/合规/领域红线在规则引擎（可独立维护、零训练成本、按需选裁）。**这就是「受约束的生成模型」**——既保留生成灵活性，又保证输出不越红线。

### 4.2 规则引擎的裁决规则（沿用权威澄清 + v0.1.2 豁免增补）

**三条铁律（QT 定调，写作模式）**

1. **禁止 > 允许**——白名单在硬约束处失效。
2. **黑名单内部：硬约束 > 软约束**——硬为 −∞ 绝对禁止，软为降权仍允许。
3. **白名单要生效的前提**：对应黑名单行是**软约束**，或该行硬约束**已获用户豁免**。

**裁决细则**

- 硬约束命中 → logits 置 −∞，**白名单在其上直接失效**（绝对禁止）。
- 仅软约束 → 降权（不删除，约束侧仍视为可回答）。
- 软 ∩ 白 → 白名单不失效、仍享加成，但**净值 clamp 至 ≤ 原始 logit**（白名单不得抵消软约束惩罚 = 「禁止永远 > 允许」的可操作实现）。

**硬约束三级（v0.1.2 新增）**

| 级别 | 含义 | 可否豁免 | AI 行为 |
|---|---|---|---|
| **L0 绝对硬** | 中国现行法律法规中的强制性禁止性规定（初始清单 = 全部相关法律） | 默认否 | 静默拒绝 + 记审计，**不询问** |
| **L1 可豁免硬** | 领域红线 / 风格红线 / 人设红线 / 变量排除结论（近期适用） | 可 | 发起询问 + 建议值 + 影响报告 |
| **L2 软约束** | 降权，仍允许 | 无需申请 | 白名单直接生效 |

**白名单豁免协议（v0.1.2 新增）**

> 定性：**这是「用户改规则」，不是「AI 破规则」。** 未经授权时硬约束绝对优先（`resolve()` 逻辑一字不改）；授权后是用户在该作用域内把「那一行」硬约束**定向降级**，不是删除。因此「禁止永远 > 允许」依然成立。

- 实现方式：在 `resolve()` **之前**加一层 `WaiverRegistry` 规则变换（已豁免的 `hard_id` 定向降为软），核心裁决实现不动。
- 建议值算法：**可行域投影** `suggest = argmin_{x ∈ Domain(v) \ blocked} d(x, x_proposed)`（想写「愤怒 0.9」而硬约束「≤ 0.7」→ 建议 0.7）。
- 防滥用：默认 deny / 定向降级（绝不全局删红线）/ 询问记忆（同一对不重复问）/ 会话配额 / 全量审计 / `always` 档默认关闭。

详见 `HEv7.5_变量引擎与约束裁决设计_v0.1.md` §5、§6。

### 4.3 规则子集化（G4 的可操作实现）

- `RuleConstrainedGenerator` 支持 `rule_selector(AnalysisContext) -> CompositeVerdict`：给定 CLM 的分析上下文，**只返回本次相关的规则子集**（例如按领域从规则库中挑出该领域对应的硬/软/白），而非全量。
- 静态全量红线（`hard/soft/white` 全局 id）与动态 Trie 红线（`verdict_fn(ctx_ids)`）作为兜底仍保留；三者按 union 合并施加。
- 见 `T1/src/t1/rfp_core.py`：`AnalysisContext` / `RuleSelector` / `merge_verdicts` / `make_domain_selector`。

### 4.4 推理流程（生成循环）

1. CLM 产出【分析上下文】，作为生成前缀 / 条件输入，**同时喂给规则引擎的 `rule_selector` 决定本次规则子集**。
2. 每一步：概率引擎 → next-token logits → 规则引擎（选中的子集 + Trie）裁决 → 采样或贪心选 token → 拼回上下文。
3. 循环至 EOS 或长度上限，得到生成初稿。
4. 初稿送 TRA 三反思（可多轮回灌，必要时调用外部检索占位），再送变量引擎做长文变量校验，最后由概率引擎汇总定稿。

### 4.5 训练目标

- **主损失 L_gen**：自回归 next-token 交叉熵（在语料上）。
- **辅助损失 L_causal**：因果一致性（结构因果，果不得超因），**训练期注入**（因果引擎职责）。
- **规则正则 L_rule**：训练时对命中硬约束的 token 加重惩罚，使模型内部化红线；推理时再用 logits_processor 硬性兜底（双保险）。
- **条件输入**：CLM 给出的领域标签可作为生成 prefix，引导领域正确生成。

## 5. 其余组件在 T1 的角色

### 5.1 CLM 字符引擎（问题分析 + 规则选裁依据）

不负责生成最终回答，只做前端分析：把 query 拆成字符/语义原子、识别领域、抽取关键变量，产出【分析上下文】。**这份分析上下文同时决定 RPF 核心"本次用哪些规则"**——是规则引擎选规则的唯一输入来源。是生成的前置理解层。

### 5.2 TRA 推理控制器（第二步·搜集信息）

对 RPF 核心生成的草稿做三次反思——一致性、合规、完整性——输出修订指令回灌生成，可多轮迭代。保证最终回答不仅「能生成」，还「经得起反思」。

- **对外检索（占位）**：反思/搜集阶段需要事实或资料时，调用 **百度** 或 **QT浏览器**。⚠ **QT浏览器目前尚未开座（QT 计划自研，未启动），当前为占位接口**，待其就绪后接入真实检索；在此之前 TRA 的"搜集信息"走占位/本地知识。

### 5.3 变量引擎（7.5 提前 · v0.1.2 修订）

确定性无参，面向**长文本**生成时维护**变量树**（VariableExtractor → RelationModeler → PropagationEngine → ExclusionSolver）。

**变量模型**：主变量（角色 / 模块 / 场景）+ 多个子变量（性格、爱好、关系、状态…）。三类量必须分开，混用会算错：

| 概念 | 语义 | 位置 | 是否随时间变 |
|---|---|---|---|
| 强度 intensity | 变量当前取值的量 | 变量上 | 变 |
| 权重 weight | 一条边的影响力 | 关系边上 | 基本不变 |
| 置信 confidence | 该取值有多确定 | 变量上 | 变（决定约束硬度） |

**传播**：带权传播 `Δv_j = clamp(Σ_i w_ij·Δv_i·λ, -1, +1)`，**迭代至不动点**（角色互影响必有环，BFS 深度截断会漏回弹）。冲突记**强度**而非布尔，超阈值才按置信映射为硬 / 软约束。

**排除结论的作用域（QT 裁定）**：排除结论（如「角色已死」）**带作用域，不是无条件硬约束**，且**一律必须询问**：

| 用户裁定 | 约束类型 | 级别 | 后果 |
|---|---|---|---|
| 真死 | 真硬约束 | L0 | 角色不再出现于文中；不可豁免 |
| 文中已死 | 近期适用约束 | L1 | 自该叙事点起生效；后续可豁免（复活 = 剧情转折） |

不占参数预算，任何规模零成本。详见 `HEv7.5_变量引擎与约束裁决设计_v0.1.md` §2–§5。

### 5.4 因果引擎（7.5 提前 · **双角色**，v0.1.2 修订）

> ⚠️ **本节原措辞「明确不在推理主链」已作废**（QT 2026-10-03 拍定 D1）。因果引擎升级为**训练期注入 + 推理期分支仲裁**双角色。

- **训练期**：L_causal 把「有因必有果」一致性注入概率引擎，使生成分布不得把概率堆到规则不允许的位置（与综合名单「禁止 > 允许」同构）。
- **推理期 · 分支仲裁（新增）**：在 BranchEvaluator 中为候选续写打 **CausalSufficiency（因果充分性）分**——该候选的「果」是否有「因」支撑（未铺垫的背叛 = 无因之果 = 扣分），与变量引擎的一致性分加权后择优。

**分支推演流程（BranchEvaluator）**：

```
状态 S_t → 概率引擎出 N 个候选 → 确定性解析各候选的 delta_i
        → 沙箱试算（不真改状态）→ 变量引擎打一致性/副作用分 + 因果引擎打因果充分性分
        → 加权仲裁选 c* → 提交 delta*，落选分支回滚
```

**分支粒度**：不固定 N，运行时自适应——仅当 top-1/top-2 分歧度低于阈值、或变量引擎报出冲突时才展开 N 路，否则单路直出（省 N 倍开销）。

详见 `HEv7.5_变量引擎与约束裁决设计_v0.1.md` §4。

### 5.5 概率引擎（最终出回答）

T1 唯一的生成主干，贯穿两处：
1. RPF 核心的受约束 token 循环内部（被规则引擎约束着生成初稿）；
2. 流程末尾，汇总【分析上下文 + 规则约束结果 + TRA 修订 + 变量/因果结论】，**生成最终回答内容**。

所有"理解/约束/反思/校验"的最终落点都是它——这也是为什么流程末尾再次显式点出"全部交给概率引擎生成回答"。

### 5.6 7.5 文档搬迁

变量引擎、因果引擎的定义与实现来源为 HEv7.5 的确定性引擎。T1 资料库归档需把 7.5 架构演进文档中对应的"变量引擎 / 因果引擎"章节**搬迁或引用**进来，作为这两块引擎的权威出处（见 §1.5）。

## 6. 代码落地（T1/src/t1/ 隔离包）

原则：**隔离、复用、不破坏现有 HEv6/7**。

- `T1/src/t1/rfp_core.py`：
  - `ProbabilityEngine`（自回归生成器：Embedding + LSTM + 解码头，MX150 安全）。
  - `RuleConstrainedGenerator`（封装概率引擎 + 规则引擎，对外开放 `generate(prefix, analysis)`）。
  - `AnalysisContext` / `RuleSelector` / `merge_verdicts` / `make_domain_selector`（**规则子集化**：按分析上下文选规则，非全量启动）。
- `T1/scripts/train_t1.py`：训练概率引擎（L_gen + L_causal + L_rule），沿用 trainbench 纪律红线。
- `T1/scripts/generate_t1.py`：支持 `--rule-bank`（按领域选规则）+ `--domain` 构建分析上下文，演示规则子集化；向后兼容 `--rule-policy` 静态全量。
- **复用**（不重写，直接引用权威实现）：
  - `src/rf_moe/services/composite_list.py` —— 规则裁决（`resolve(hard, soft, white)`）。
  - `src/rf_moe/services/logits_processor.py` —— logits 施加裁决（numpy/torch 双路径）。
  - `src/rf_moe/services/variable_engine.py` —— 变量引擎（`build_state`）。
  - `CausalConsistencyLoss`（因果一致性，已在训练骨架落地，训练期专用）。
- **引用**（沿用 7.0 既有组件）：
  - `src/services/clm/` —— CLM 字符引擎（问题分析 + 规则选裁依据）。
  - 举一反三 / TRA 模块 —— 推理控制器（三反思 + 多轮回灌 + 外部检索占位）。
