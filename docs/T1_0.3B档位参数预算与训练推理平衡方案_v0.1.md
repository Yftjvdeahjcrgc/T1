# T1 概率引擎 0.3B 档位参数预算与训练/推理平衡方案 v0.1

> 定稿日期：2026-10-03
> 适用前提：**训练**迁到外部 CPU 训练机（8 核 / 32GB 内存）；**推理**仍回本机 MX150 2GB（电脑配置不变）。
> 资料库正本：https://www.workbuddy.cn/space/d/rNd8qZmkjOPsFKVOT0eFqX （T1 特一 文件夹）

---

## 1. 结论速览（TL;DR）

1. **0.3B 可以训，也可以在本机推理**——训练机 32GB 内存装得下（峰值约 10GB），MX150 2GB 装得下 fp16 权重（595MB）。
2. **参数量 ≠ 训练成本**：Embedding 是查表，训练时不花 FLOPs；LSTM 与 head 才是按 token 计费的"稠密"部分。0.3B 的平衡点是**把参数尽量挪到 Embedding**。
3. **推理是带宽受限**，不是算力受限：自回归每生成一个 token 要把权重读一遍。0.3B fp16 ≈ 40 tok/s，int8 ≈ 80 tok/s——能跑，但不快。
4. **真正的短板是语料**，不是算力也不是显存：当前语料 10.7 万 token 对 0.3B 参数，比例 0.0004 token/param，模型只会记忆不会泛化。**要么扩语料，要么降档。**

---

## 2. 直接回答：推理时总参数是多少

| 项目 | 数值 |
| --- | --- |
| 0.3B 档位实际参数量 | **297M（0.297B）** |
| fp32 推理权重 | 1189 MB — MX150 2GB 上**不建议**（剩不下激活空间） |
| fp16 推理权重 | **595 MB — 可行**（可用约 1.6GB，留 ~1GB 给激活） |
| int8 推理权重 | 297 MB — 最稳，速度也最快 |
| 推理速度（MX150，带宽 48GB/s） | fp16 ≈ 40 tok/s；int8 ≈ 80 tok/s |
| 原 0.124B 档对比 | 159M 参数 / fp16 317MB / ≈76 tok/s |

结论：**0.3B 用 fp16 或 int8 推理，MX150 2GB 装得下、跑得动。**

---

## 3. 0.3B 怎么凑（参数拆分）

| 档位 | 结构 V/E/H/L | 总参 | Embedding | LSTM | head | 稠密(计费) | fp16 权重 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| edge_16m | 8000/256/768/2 | 0.016B | 2.0M | 7.9M | 6.2M | 14.0M | 32MB |
| gen_0p124b | 8000/1024/3072/2 | 0.159B | 8.2M | 125.9M | 24.6M | 150.5M | 317MB |
| **gen_0p3b（推荐）** | **48000/2048/2048/3** | **0.297B** | 98.3M | 100.7M | 98.4M | 199.1M | **595MB** |
| gen_0p3b_fast | 64000/2560/1280/3 | 0.292B | 163.8M | 45.9M | 82.0M | 127.9M | 583MB |

设计原则：

- **参数往 Embedding 挪**——Embedding 是查表，训练时只有被命中的行参与梯度，不计 FLOPs；
- **head 的 H×V 决定 GEMM 成本**，是 CPU 训练最大单项，词表不能盲目翻倍；
- **E 与 H 尽量同量级**——宽进窄出（如 E=3072 / H=1024）会造成信息瓶颈，生成质量受损；
- `gen_0p3b_fast` 是同一参数量下的"CPU 速度档"：稠密部分从 199M 压到 128M，训练快约 1.5 倍，代价是隐层只有 1280 维。

## 4. 训练侧：8 核 CPU / 32GB 可行性

算力基线来自本机实测（i7-8550U 4 物理核 / torch 2.12.1+cpu）：
V=8000 / E=256 / H=768 / L=2（16.1M，稠密 14.0M）→ 4 线程 636 tok/s ≈ **53.5 GFLOPS 有效算力**
（LSTM 在 CPU 上只有约 18% 峰值效率，循环 kernel 吃不满 AVX，不能拿 CPU 理论 FLOPS 直接除。）

外推到目标机：53.5 × 核数比 2.0 × 频率架构比 1.3 × 多核并行效率 0.85 ≈ **118 GFLOPS**。

| 档位 | 稠密 | GFLOP/token | 自动 batch | 峰值内存 | tok/s | 1 epoch | 6h 可跑 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| edge_16m | 14.0M | 0.084 | 256 | 1.58GB | 1405 | 1.3min | 285 epoch |
| gen_0p124b | 150.5M | 0.903 | 256 | 3.93GB | 131 | 13.6min | 26.5 epoch |
| **gen_0p3b** | 199.1M | 1.194 | 256 | 10.28GB | 99 | 17.9min | 20.1 epoch |
| gen_0p3b_fast | 127.9M | 0.767 | 217 | 10.30GB | **154** | 11.5min | 31.2 epoch |

内存不是瓶颈：0.3B 用 SGD 峰值约 10.3GB，换 AdamW 约 15GB，32GB 都很宽松。
batch 由 `--ram-budget-gb` 自动推，并给 logits(B, T, V) 单项设 35% 的预算上限——否则它会独自吃掉 14GB，把训练推进内存带宽瓶颈。

## 5. 推理侧：MX150 2GB

| 档位 | fp32 | fp16 | int8 | fp16 tok/s | int8 tok/s | MX150 2GB 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| gen_0p124b | 635MB | 317MB | 159MB | 76 | 151 | 可行 |
| **gen_0p3b** | 1189MB | **595MB** | **297MB** | **40** | **81** | fp32 不建议；fp16 / int8 可行 |
| gen_0p3b_fast | 1167MB | 583MB | 292MB | 41 | 82 | fp32 不建议；fp16 / int8 可行 |

自回归解码是**带宽受限**：每生成一个 token，要把全部权重从显存读一遍（GEMV，不是 GEMM）。
上限 = 显存带宽 48GB/s ÷ 权重字节数；实际按 5 折估算。这也是为什么 0.3B 在 MX150 上"装得下但不快"。

## 6. 语料：真正的短板

| 档位 | 当前语料 token/param | 判定 | 建议最小语料(2×) | 理想语料(20×) |
| --- | --- | --- | --- | --- |
| edge_16m | 0.007 | 严重不足 | 3200 万 | 3.2 亿 |
| gen_0p124b | 0.001 | 严重不足 | 3.17 亿 | 31.7 亿 |
| **gen_0p3b** | **0.0004** | **严重不足** | **5.95 亿** | **59 亿** |
| gen_0p3b_fast | 0.0004 | 严重不足 | 5.83 亿 | 58 亿 |

训练脚本启动时会自动打印 `token-per-param` 并在 < 2 时报警。
按 Chinchilla 标度，0.3B 的理想语料是 **59 亿 token**；现实可接受下限（2×）也需 **5.95 亿 token**。
当前 10.7 万 token 差 3～4 个数量级——**0.3B 在当前语料上只会记忆，谈不上有泛化能力。**

三条可选路线：

- **路线 A（推荐）**：0.3B 结构照建（对齐 7.5 主线档位），但**先扩语料**再谈能力。短期目标是 ≥ 3 亿 token。
- **路线 B**：语料短期扩不动 → 降档到语料匹配规模（0.03B 配 100 万 token / 0.1B 配 3000 万 token）。
- **路线 C**：明确 0.3B 只做**工程可行性验证**（跑得通、规则引擎接得上、fp16 能加载），能力指标留到扩语料后再评。

## 7. 落地命令

**训练机（8 核 CPU / 32GB）：**

```bash
python T1/scripts/train_t1.py \
  --preset gen_0p3b \
  --corpus T1/data/corpus/training_corpus_with_cmmlu.jsonl \
  --out T1/data/checkpoints/t1_gen_0p3b_v01.pt \
  --device cpu --threads 8 --optim adamw \
  --batch 0 --ram-budget-gb 24 --max-seq 128 \
  --causal-weight 0.1 --max-hours 72
```

已纳管 trainbench，等价写法：

```bash
python -m trainbench run t1_gen_0p3b --set max-hours=72
```

**本机推理（MX150 2GB）：**

```bash
C:/Python314/python.exe T1/scripts/generate_t1.py \
  --ckpt T1/data/checkpoints/t1_gen_0p3b_v01.pt \
  --prompt "感冒了怎么办" --domain medical \
  --rule-bank T1/data/rules/rule_bank.json \
  --device cuda --dtype fp16 --max-len 64
```

**在训练机上实测校准算力（替换预算脚本里的外推假设）：**

```bash
python T1/scripts/budget_0p3b.py --bench --threads 8 --target-cores 8
```

## 9. 遗留项

- **语料扩充**：0.3B 的能力前提是 ≥ 3 亿 token，需单独排期。
- **INT8 量化导出**：`quantize` 任务仍是 planned；0.3B 在本机推理若要稳定 80 tok/s，需要它。
- **架构选型**：当前仍是 LSTM。T1 最终要接回 7.5 / 100B 主线（Transformer），且 Transformer 在 CPU 上是纯大 GEMM、效率显著高于 LSTM；是否在 0.3B 档就切 Transformer，待定。
